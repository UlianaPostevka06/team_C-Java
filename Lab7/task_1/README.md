# Завдання 1. Single Responsibility Principle (SRP) - Library Loan Manager

## 1. Предметна область

Автоматизована система міської бібліотеки обробляє повернення книг: перевіряє читацький квиток і дані видачі, розраховує пеню за прострочення (або бонусні бали за вчасне повернення), формує акт повернення, оновлює електронний каталог і надсилає читачеві квитанцію електронною поштою.

## 2. Проблеми вихідного («поганого») коду

Уся логіка була в одному методі `LibraryLoanService.ProcessBookReturn`, який виконував п'ять різних робіт.

| № | Проблема | Де проявляється | Порушений принцип |
|---|----------|-----------------|-------------------|
| 1 | Клас має **п'ять причин для змін**: правила валідації, тарифи й бонуси, текст акта, формат збереження, канал сповіщення | `ProcessBookReturn` | **SRP** (головне порушення завдання) |
| 2 | Прямий запис у файл `File.AppendAllText` усередині бізнес-логіки | крок 4 методу | DIP, складність тестування |
| 3 | Прямий виклик `SmtpClient` / `MailMessage` з жорстко заданими адресами | крок 5 методу | DIP, складність тестування |
| 4 | «Магічні числа» `15.00m` (штраф за день) і `10` (бонусні бали) без імен | розрахунок | читабельність, DRY |
| 5 | Умова `overdueDays > 0` повторюється тричі: у розрахунку, у тексті акта й у темі листа | кроки 2, 3, 5 | **DRY** |
| 6 | Метод довгий (понад 60 рядків) і змішує різні рівні абстракції | весь метод | **KISS** |
| 7 | Змінні-«супутники» `fineAmount` і `loyaltyPointsEarned` передаються між кроками неявно, через локальний стан | початок методу | чистота коду |
| 8 | Рядок `$"Книга: "{loan.BookTitle}"..."` містить вкладені лапки, і код **не компілюється** | крок 3 | синтаксична помилка |
| 9 | Властивості моделі `string` без значення за замовчуванням (можливі `null`) | `BookReturnModel` | безпека типів |

### Чому це проблема на практиці

- **Ризик регресії.** Щоб змінити ставку штрафу, треба відкрити метод, який також відправляє пошту й пише у файл. Помилка може зламати все одразу.
- **Конфлікти в команді.** Один розробник змінює тарифи, інший формат листа, третій спосіб збереження, і всі правлять один і той самий метод.
- **Складність тестування.** Перевірити розрахунок штрафу неможливо без запису у файл і спроби підключитися до SMTP-сервера.
- **Метод росте необмежено.** Кожна нова вимога (SMS-сповіщення, нова знижка) збільшує його розмір і складність.

## 3. Що було зроблено

### 3.1. Аналіз причин для змін (reasons to change)

| Причина для зміни | Хто її ініціює | Новий клас |
|---|---|---|
| Правила перевірки даних | юристи, адміністрація | `LoanValidator` |
| Тарифи штрафу та бонуси | фінансовий відділ | `FineCalculator` |
| Вигляд і текст повідомлення | служба підтримки | `NoticeFormatter` |
| Формат і місце зберігання каталогу | ІТ-відділ | `CatalogRepository` |
| Канал і параметри доставки | ІТ-відділ | `EmailNotifier` |
| Порядок кроків обробки | аналітики процесів | `LibraryLoanService` (оркестратор) |

### 3.2. Нова структура

| Клас / тип | Роль |
|---|---|
| `BookReturnModel` | Доменна модель: дані про повернення книги. Рядкові властивості мають значення `string.Empty` за замовчуванням, тому `null` не з'являється |
| `ReturnAssessment` (`record`) | Результат розрахунку: `OverdueDays`, `FineAmount`, `LoyaltyPoints`. Властивість `IsOverdue` є єдиним місцем, де визначається, що повернення прострочене |
| `LoanValidator` | Тільки валідація даних. Кидає виняток, якщо дані некоректні |
| `FineCalculator` | Тільки бізнес-логіка: прострочення, штраф, бонус. Тариф винесено в константи `FinePerDay` і `OnTimeBonusPoints` |
| `NoticeFormatter` | Тільки формування тексту акта повернення |
| `CatalogRepository` | Тільки запис історії повернень у файл каталогу |
| `EmailNotifier` | Тільки надсилання листа. Помилка відправки обробляється всередині й не ламає процес |
| `LibraryLoanService` | **Оркестратор**: лише викликає кроки по черзі, сам нічого не рахує |
| `Program` | **Точка збірки**: створює конкретні об'єкти й передає їх в оркестратор |

Усі класи перебувають в одному файлі й розділені за призначенням. Їх можна винести в окремі файли без жодних змін у коді.

### 3.3. Було і стало (ключовий фрагмент)

**Було** (усе в одному методі):

```csharp
public void ProcessBookReturn(BookReturnModel loan)
{
    // 1. валідація ...
    // 2. розрахунок штрафу ...
    // 3. формування тексту ...
    // 4. File.AppendAllText(...)
    // 5. SmtpClient.Send(...)
}
```

**Стало** (лише координує):

```csharp
public void ProcessBookReturn(BookReturnModel loan)
{
    _validator.Validate(loan);

    ReturnAssessment assessment = _calculator.Calculate(loan);
    string notice = _formatter.Format(loan, assessment);
    Console.WriteLine(notice);

    _repository.SaveReturn(loan);
    _notifier.Send(loan, assessment, notice);
}
```

Розрахунок тепер зосереджений в одному місці:

```csharp
return overdueDays > 0
    ? new ReturnAssessment(overdueDays, overdueDays * FinePerDay, 0)
    : new ReturnAssessment(overdueDays, 0, OnTimeBonusPoints);
```

### 3.4. Оцінка за метриками

Значення орієнтовні. WMC обчислено як сумарна цикломатична складність методів класу, CBO як кількість пов'язаних із класом користувацьких і бібліотечних типів.

| Клас | WMC | CBO | LCOM |
|---|---|---|---|
| `LibraryLoanService` (до) | ≈ 7 | ≈ 7–8 | формально не інформативний (немає полів), логічно низька зв'язність |
| `LoanValidator` | 4 | 3 | 0 (без стану) |
| `FineCalculator` | 2 | 2 | 0 (немає екземплярних полів) |
| `NoticeFormatter` | 2 | 2 | 0 (без стану) |
| `CatalogRepository` | 1 | 2 | 0 |
| `EmailNotifier` | 3 | 5 | 0 (без стану) |
| `LibraryLoanService` (після) | 1 | 8 | 0 (усі 5 полів використовує метод `ProcessBookReturn`) |

**Висновки за метриками:**

- **WMC.** Складність 7 в одному класі розподілена між п'ятьма класами, жоден із яких не перевищує 4. Кожен із них легко читати й тестувати окремо.
- **CBO.** Для нових сервісних класів зв'язність низька (2–5). Показник оркестратора вищий, тому що він залежить від п'яти сервісів. Це очікувана ціна декомпозиції. Зменшити її можна в Завданні 5 (DIP), замінивши конкретні класи абстракціями.
- **LCOM.** Нові класи мають високу зв'язність: усі їхні методи й поля працюють на одну відповідальність.

## 4. Застосування принципів SOLID

### S: Single Responsibility (основне завдання)

Кожен клас має одну причину для змін:

- змінилися правила перевірки даних: змінюється лише `LoanValidator`;
- змінився тариф штрафу або бонус: змінюється лише `FineCalculator`;
- змінився текст чи вигляд акта: змінюється лише `NoticeFormatter`;
- змінився формат або місце збереження історії: змінюється лише `CatalogRepository`;
- змінився канал або параметри доставки (SMTP, SMS): змінюється лише `EmailNotifier`;
- змінився порядок кроків: змінюється лише `LibraryLoanService`.

### Підготовка до наступних принципів

Це завдання присвячене SRP, тому інші принципи реалізовано лише частково:

- **DI.** Залежності вже передаються через конструктор (Constructor Injection), а конкретні об'єкти створюються тільки в `Main`. Service Locator не використовується.
- **DIP.** Оркестратор поки що залежить від конкретних класів, а не від інтерфейсів. Повну інверсію залежностей буде виконано в Завданні 5.
- **OCP, LSP, ISP.** Наслідування й «жирних» інтерфейсів у цьому коді немає, тому ці принципи розглядаються в Завданнях 2–4.

## 5. Прагматичні принципи

### DRY

- **Єдине джерело правди для «прострочення».** Умова `overdueDays > 0` повторювалася тричі (розрахунок, текст акта, тема листа). Тепер вона існує лише як властивість `ReturnAssessment.IsOverdue`, і її використовують `NoticeFormatter` та `EmailNotifier`.
- **Єдине джерело правди для тарифів.** Числа `15.00m` і `10` існують лише як іменовані константи `FinePerDay` і `OnTimeBonusPoints` у `FineCalculator`.
- **Текст акта формується один раз** і використовується повторно: для виводу в консоль та як тіло листа.

### KISS

- Метод оркестратора має лінійну логіку без розгалужень і вкладеності: п'ять послідовних викликів.
- Довгий метод (понад 60 рядків) розбито на короткі, зрозумілі методи, кожен із яких робить одну річ.
- Валідатор використовує перевірки з негайним викиданням винятку (Guard Clauses) без вкладених `if`, тому кожну умову видно окремо.
- Розрахунок записано одним тернарним виразом із поверненням готового результату замість змінних, що змінюються по гілках.
- Помилку відправки листа оброблено всередині `EmailNotifier`, тож решта коду не засмічена `try/catch`.

### YAGNI

- Не створено зайвих інтерфейсів, абстрактних базових класів, фабрик, конфігураційних файлів та IoC-контейнера. Вони не потрібні для поточного завдання. Інтерфейси з'являться в Завданні 5, коли для них буде реальна потреба (підміна реалізацій).
- Кожен виділений клас відповідає реальній причині для змін із таблиці 3.1. Дроблення «про запас» немає.
- `ReturnAssessment` є невеликим `record` із трьох полів і однієї властивості. Це необхідний результат розрахунку, а не надлишкова абстракція.
- Немає заглушок «на майбутнє» та методів із `NotImplementedException`.

## 6. Відмінності від вихідної поведінки

Бізнес-результат розрахунку (прострочення, штраф, бонус), текст акта, запис у каталог і лист читачеві **не змінилися**. Свідомо змінено таке:

1. **Виправлено синтаксичну помилку.** Вкладені лапки у рядку «Книга: "…"» замінено на «ялинки» (`«{loan.BookTitle}»`), інакше вихідний код не компілювався.
2. **Додано вивід акта в консоль.** Оркестратор виконує `Console.WriteLine(notice)`, чого у вихідному методі не було. Це зроблено для наочної демонстрації результату.
3. **Властивості моделі отримали значення `string.Empty` за замовчуванням.** Валідація використовує `IsNullOrWhiteSpace`, тож результат перевірки не змінився.
4. **Додано `Main` із прикладом даних** (точка збірки й демонстрація роботи). У вихідному фрагменті точки входу не було.
5. **Правило валідації дати** (`ActualReturnDate < ExpectedReturnDate.AddYears(-1)`) збережено без змін, щоб не змінювати поведінку. Число «1 рік» можна у майбутньому винести в іменовану константу.
