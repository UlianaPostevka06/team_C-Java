## 1. Предметна область

Страхова компанія розраховує річну премію залежно від типу полісу (`AUTO`, `HEALTH`, `PROPERTY`, `TRAVEL`) і характеристик клієнта (вік, страхова сума, наявність попередніх страхових випадків).

## 2. Проблеми вихідного («поганого») коду

Увесь розрахунок був в одному методі `calculatePremium` з ланцюгом `if / else if` за значенням `enum PolicyType`.

| № | Проблема | Де проявляється | Порушений принцип |
|---|----------|-----------------|-------------------|
| 1 | Додавання нового типу полісу вимагає **змінювати вже протестований метод** (нова гілка `else if`) | `calculatePremium` | **OCP** (головне порушення завдання) |
| 2 | Клас має кілька причин для змін: правила 4 видів страхування, округлення, формат і вивід логу | `InsurancePremiumCalculator` | **SRP** |
| 3 | Прямий виклик `System.out.println` усередині бізнес-логіки: не можна підмінити вивід, складно тестувати | кінець методу | **DIP** |
| 4 | «Магічні числа» (`0.03`, `1.20`, `25`, `40`, `65`, `150.00`...) розкидані по гілках без імен | усі гілки | читабельність, **DRY** |
| 5 | Складна логіка в одному методі: вкладені `if` усередині гілок, висока цикломатична складність | `calculatePremium` | **KISS** |
| 6 | Змінна `basePremium` ініціалізується `ZERO` і перезаписується в кожній гілці; `else` з винятком змішаний з бізнес-правилами | початок методу | **KISS** |
| 7 | `PolicyHolder` не перевіряє дані при створенні (від'ємний вік або сума, `null`) | конструктор | fail-fast, інваріанти |
| 8 | Неідіоматичний геттер `isHasPriorClaims()` | `PolicyHolder` | чистота коду |
| 9 | Всі класи в одному файлі | весь файл | організація коду |

### Чому це проблема на практиці

- **Ризик регресії.** Щоб додати страхування життя, треба відкрити робочий метод і додати гілку. Одна помилка може зламати розрахунок для всіх інших полісів, тому доведеться перетестовувати все.
- **Конфлікти в команді.** Кілька розробників, які додають різні типи полісів, правитимуть той самий метод.
- **Складність тестування.** Правило кожного типу полісу не можна перевірити окремо від решти.
- **Метод росте необмежено.** Кожен новий тип збільшує складність методу.

## 3. Що було зроблено

### 3.1. Нова структура


| Файл | Роль |
|------|------|
| `InsurancePremiumCalculator.java`  Інтерфейси-абстракції (**точка розширення** `PremiumStrategy`) і оркестратор, який знаходить стратегію, округлює результат і логує |
| `PremiumStrategies.java` | Стратегії: по одній на тип полісу, кожна містить тільки своє правило. `LifePremiumStrategy` — демонстрація OCP |
| `PolicyHolder.java` | Enum-ключ пошуку стратегії і незмінна доменна сутність із перевіркою даних при створенні |
| `Main.java` | **Composition Root**: єдине місце, де створюються конкретні об'єкти |

Класи в межах одного файлу розділені за призначенням. Окремі файли для кожного класу не створювалися: усі допоміжні типи непублічні (package-private), а публічними залишено лише `InsurancePremiumCalculator`, `PolicyHolder` і `Main`. Принципи SOLID від цього не залежать: стратегії залишаються окремими класами, а новий тип полісу додається новим класом. Якщо потрібен окремий файл для кожного класу, їх можна розділити без змін коду.

### 3.2. Було і стало (ключовий фрагмент)

**Було:**

```java
if (type == PolicyType.AUTO) { ... }
else if (type == PolicyType.HEALTH) { ... }
else if (type == PolicyType.PROPERTY) { ... }
else if (type == PolicyType.TRAVEL) { ... }
else { throw new IllegalArgumentException(...); }
```

**Стало:**

```java
PremiumStrategy strategy = strategies.get(type);
if (strategy == null) {
    throw new IllegalArgumentException("Тип страхування " + type + " не зареєстровано у системі.");
}
BigDecimal premium = strategy.calculate(holder).setScale(SCALE, RoundingMode.HALF_UP);
```

Реєстр `Map<PolicyType, PremiumStrategy>` (`EnumMap`) заповнюється через конструктор зі списку стратегій.

## 4. Застосування принципів SOLID

### S: Single Responsibility
Кожен клас має одну причину для змін:
- правило страхування змінилося: змінюється лише відповідна `*PremiumStrategy`;
- змінилося округлення: змінюється лише `InsurancePremiumCalculator`;
- змінився формат або місце виводу логу: змінюється лише `PremiumLogger` і його реалізація.

### O: Open/Closed (основне завдання)
- **Точка розширення:** інтерфейс `PremiumStrategy`.
- **Додавання нового типу полісу** (на прикладі `LIFE`) потребує:
  1. нового класу `LifePremiumStrategy implements PremiumStrategy`;
  2. реєстрації стратегії в точці збірки (`Main`);
  3. нового значення в `enum PolicyType`: це одна константа без логіки.
- **Код `InsurancePremiumCalculator` і чотирьох існуючих стратегій не змінюється:** жодного рядка. Це підтверджено в `Main`: без реєстрації `LIFE` калькулятор видає помилку, після реєстрації розраховує премію.

### L: Liskov Substitution
Усі стратегії взаємозамінні: приймають коректного `PolicyHolder` і повертають невід'ємну премію без додаткових передумов. Немає `NotImplementedException`, немає стратегій із посиленими передумовами. Коректність вхідних даних гарантує сам `PolicyHolder` (див. нижче).

### I: Interface Segregation
`PremiumStrategy` має лише два методи, обидва обов'язкові для кожної реалізації. `PremiumLogger` має один метод. Порожніх методів-заглушок немає.

### D: Dependency Inversion
- `InsurancePremiumCalculator` залежить від абстракцій `PremiumStrategy` і `PremiumLogger`, а не від конкретних класів і `System.out`.
- Залежності передаються через конструктор (Constructor Injection).
- Конкретні об'єкти створюються тільки в `Main`.
- Service Locator не використовується.
- Для тестів можна підставити будь-який `PremiumLogger` (наприклад, лямбду `m -> {}`), що й зроблено в перевірці еквівалентності.

## 5. Прагматичні принципи

### DRY
- **Єдине місце округлення.** `setScale(2, HALF_UP)` було в одній гілці-фіналі; тепер воно в оркестраторі, і жодна стратегія його не дублює.
- **Єдине джерело правди для бізнес-правил.** Кожне правило (ставка, надбавка, вікові пороги) існує лише в одній стратегії як іменована константа. Число `1.20` або `25` більше не зустрічається як «голе» значення.
- **Єдине місце повідомлення про помилку** для незареєстрованого типу.

### KISS
- Усунено ланцюг `if/else if` і вкладені умови: метод оркестратора має лінійну логіку без розгалужень, окрім перевірки на `null`.
- Умови розрахунку записані короткими виразами: наприклад, у `HealthPremiumStrategy` гілку «якщо вік > 40» замінено на `Math.max(0, age - 40)`, що дає той самий результат без вкладеного `if`.
- Кожна стратегія мала малий розмір (кілька рядків) і зрозумілу структуру.
- Для реєстру використано стандартний `EnumMap`; жодних рефлексій, сканування класпасу або IoC-контейнерів.

### YAGNI
- Не додано абстрактних базових класів для стратегій, фабрик, конфігураційних файлів і IoC-контейнера: вони не потрібні для поточного завдання.
- Абстракції (`PremiumStrategy`, `PremiumLogger`) необхідні: перша є вимогою OCP, друга виносить побічний ефект (вивід) з бізнес-логіки.
- Немає заглушок «на майбутнє» і `NotImplementedException`.
- `LifePremiumStrategy` існує як навчальна демонстрація OCP за вимогою завдання; її правило (1% від суми + $5 за кожен рік після 50) умовне і не взяте з предметної області.

## 6. Відмінності від вихідної поведінки

Бізнес-результат розрахунку **не змінився**. Свідомо змінено таке:

1. `PolicyHolder` тепер відхиляє некоректні дані (від'ємний вік або сума, `null`, порожній ідентифікатор). Раніше такі об'єкти створювалися без помилок.
2. Геттер `isHasPriorClaims()` перейменовано на `hasPriorClaims()`.
3. Калькулятор тепер створюється з переліком стратегій і логером через конструктор, а не конструктором за замовчуванням. Конструктор і допоміжні типи (`PremiumStrategy`, `PremiumLogger`, стратегії, `PolicyType`) package-private: збирати об'єкти може лише код того ж пакета (`Main`).
4. Для додавання нового типу полісу в `enum PolicyType` додається одна константа. Це єдина зміна в існуючому коді, і вона не містить логіки розрахунку. Якщо потрібна повна відсутність змін навіть тут, ключем можна зробити рядок або інтерфейс замість `enum`, але це ускладнило б код без потреби (YAGNI).
