# Завдання 1

## 1. Предметна область

Автоматизована система міської бібліотеки обробляє повернення книг: перевіряє читацький квиток і дані видачі, розраховує пеню за прострочення (або бонусні бали за вчасне повернення), формує акт повернення, оновлює електронний каталог і надсилає читачеві квитанцію електронною поштою.

## 2. Проблеми вихідного («поганого») коду

Уся логіка була в одному методі `LibraryLoanService.ProcessBookReturn`, який виконував п'ять різних робіт.

| № | Проблема | Де проявляється | Порушений принцип |
|---|----------|-----------------|-------------------|
| 1 | Клас має **п'ять причин для змін**: правила валідації, тарифи й бонуси, текст акта, формат збереження, канал сповіщення | `ProcessBookReturn` | **SRP** (головне порушення завдання) |
| 2 | Прямий запис у файл `File.AppendAllText` усередині бізнес-логіки | крок 4 методу | DIP, складність тестування |
| 3 | Прямий виклик `SmtpClient` / `MailMessage` з жорстко заданими адресами | крок 5 методу | DIP, складність тестування |
| 4 | «Магічні числа» `15.00m` (штраф за день) і `10` (бонусні бали) без імен | розрахунок | читабельність, DRY |
| 5 | Умова `overdueDays > 0` повторюється тричі: у розрахунку, у тексті акта й у темі листа | кроки 2, 3, 5 | **DRY** |
| 6 | Метод довгий (понад 60 рядків) і змішує різні рівні абстракції | весь метод | **KISS** |
| 7 | Змінні-«супутники» `fineAmount` і `loyaltyPointsEarned` передаються між кроками неявно, через локальний стан | початок методу | чистота коду |
| 8 | Рядок `$"Книга: "{loan.BookTitle}"..."` містить вкладені лапки, і код **не компілюється** | крок 3 | синтаксична помилка |
| 9 | Властивості моделі `string` без значення за замовчуванням (можливі `null`) | `BookReturnModel` | безпека типів |

### Чому це проблема на практиці

- **Ризик регресії.** Щоб змінити ставку штрафу, треба відкрити метод, який також відправляє пошту й пише у файл. Помилка може зламати все одразу.
- **Конфлікти в команді.** Один розробник змінює тарифи, інший формат листа, третій спосіб збереження, і всі правлять один і той самий метод.
- **Складність тестування.** Перевірити розрахунок штрафу неможливо без запису у файл і спроби підключитися до SMTP-сервера.
- **Метод росте необмежено.** Кожна нова вимога (SMS-сповіщення, нова знижка) збільшує його розмір і складність.

### 3.3. Було і стало (ключовий фрагмент)

**Було** (усе в одному методі):

```csharp
public void ProcessBookReturn(BookReturnModel loan)
{
    // 1. валідація ...
    // 2. розрахунок штрафу ...
    // 3. формування тексту ...
    // 4. File.AppendAllText(...)
    // 5. SmtpClient.Send(...)
}
```

**Стало** (лише координує):

```csharp
public void ProcessBookReturn(BookReturnModel loan)
{
    _validator.Validate(loan);

    ReturnAssessment assessment = _calculator.Calculate(loan);
    string notice = _formatter.Format(loan, assessment);
    Console.WriteLine(notice);

    _repository.SaveReturn(loan);
    _notifier.Send(loan, assessment, notice);
}
```

Розрахунок тепер зосереджений в одному місці:

```csharp
return overdueDays > 0
    ? new ReturnAssessment(overdueDays, overdueDays * FinePerDay, 0)
    : new ReturnAssessment(overdueDays, 0, OnTimeBonusPoints);
```

### 3.4. Оцінка за метриками

Значення орієнтовні. WMC обчислено як сумарна цикломатична складність методів класу, CBO як кількість пов'язаних із класом користувацьких і бібліотечних типів.

| Клас | WMC | CBO | LCOM |
|---|---|---|---|
| `LibraryLoanService` (до) | ≈ 7 | ≈ 7 | формально не інформативний (немає полів), логічно низька зв'язність |
| `LoanValidator` | 4 | 3 | 0 (без стану) |
| `FineCalculator` | 2 | 2 | 0 (обидві константи використовує єдиний метод) |
| `NoticeFormatter` | 2 | 2 | 0 (без стану) |
| `CatalogRepository` | 1 | 2 | 0 |
| `EmailNotifier` | 3 | 5 | 0 (без стану) |
| `LibraryLoanService` (після) | 1 | 7 | 0 (усі 5 полів використовує метод `ProcessBookReturn`) |

**Висновки за метриками:**

- **WMC.** Складність 8 в одному класі розподілена між п'ятьма класами, жоден із яких не перевищує 4. Кожен із них легко читати й тестувати окремо.
- **CBO.** Для нових сервісних класів зв'язність низька (2–5). Показник оркестратора вищий, тому що він залежить від п'яти сервісів. Це очікувана ціна декомпозиції. Зменшити її можна в Завданні 5 (DIP), замінивши конкретні класи абстракціями.
- **LCOM.** Нові класи мають високу зв'язність: усі їхні методи й поля працюють на одну відповідальність.

## 4. Застосування принципів SOLID

### S: Single Responsibility (основне завдання)

Кожен клас має одну причину для змін:

- змінилися правила перевірки даних: змінюється лише `LoanValidator`;
- змінився тариф штрафу або бонус: змінюється лише `FineCalculator`;
- змінився текст чи вигляд акта: змінюється лише `NoticeFormatter`;
- змінився формат або місце збереження історії: змінюється лише `CatalogRepository`;
- змінився канал або параметри доставки (SMTP, SMS): змінюється лише `EmailNotifier`;
- змінився порядок кроків: змінюється лише `LibraryLoanService`.

### Підготовка до наступних принципів

Це завдання присвячене SRP, тому інші принципи реалізовано лише частково:

- **DI.** Залежності вже передаються через конструктор (Constructor Injection), а конкретні об'єкти створюються тільки в `Main`. Service Locator не використовується.
- **DIP.** Оркестратор поки що залежить від конкретних класів, а не від інтерфейсів. Повну інверсію залежностей буде виконано в Завданні 5.
- **OCP, LSP, ISP.** Наслідування й «жирних» інтерфейсів у цьому коді немає, тому ці принципи розглядаються в Завданнях 2–4.

## 5. Прагматичні принципи

### DRY

- **Єдине джерело правди для «прострочення».** Умова `overdueDays > 0` повторювалася тричі (розрахунок, текст акта, тема листа). Тепер вона існує лише як властивість `ReturnAssessment.IsOverdue`, і її використовують `NoticeFormatter` та `EmailNotifier`.
- **Єдине джерело правди для тарифів.** Числа `15.00m` і `10` існують лише як іменовані константи `FinePerDay` і `OnTimeBonusPoints` у `FineCalculator`.
- **Текст акта формується один раз** і використовується повторно: для виводу в консоль та як тіло листа.

### KISS

- Метод оркестратора має лінійну логіку без розгалужень і вкладеності: п'ять послідовних викликів.
- Довгий метод (понад 60 рядків) розбито на короткі, зрозумілі методи, кожен із яких робить одну річ.
- Валідатор використовує перевірки з негайним викиданням винятку (Guard Clauses) без вкладених `if`, тому кожну умову видно окремо.
- Розрахунок записано одним тернарним виразом із поверненням готового результату замість змінних, що змінюються по гілках.
- Помилку відправки листа оброблено всередині `EmailNotifier`, тож решта коду не засмічена `try/catch`.

### YAGNI

- Не створено зайвих інтерфейсів, абстрактних базових класів, фабрик, конфігураційних файлів та IoC-контейнера. Вони не потрібні для поточного завдання. Інтерфейси з'являться в Завданні 5, коли для них буде реальна потреба (підміна реалізацій).
- Кожен виділений клас відповідає реальній причині для змін із таблиці 3.1. Дроблення «про запас» немає.
- `ReturnAssessment` є невеликим `record` із трьох полів і однієї властивості. Це необхідний результат розрахунку, а не надлишкова абстракція.
- Немає заглушок «на майбутнє» та методів із `NotImplementedException`.

## 6. Відмінності від вихідної поведінки

Бізнес-результат розрахунку (прострочення, штраф, бонус), текст акта, запис у каталог і лист читачеві **не змінилися**. Свідомо змінено таке:

1. **Виправлено синтаксичну помилку.** Вкладені лапки у рядку «Книга: "…"» замінено на «ялинки» (`«{loan.BookTitle}»`), інакше вихідний код не компілювався.
2. **Додано вивід акта в консоль.** Оркестратор виконує `Console.WriteLine(notice)`, чого у вихідному методі не було. Це зроблено для наочної демонстрації результату.
3. **Властивості моделі отримали значення `string.Empty` за замовчуванням.** Валідація використовує `IsNullOrWhiteSpace`, тож результат перевірки не змінився.
4. **Додано `Main` із прикладом даних** (точка збірки й демонстрація роботи). У вихідному фрагменті точки входу не було.
5. **Правило валідації дати** (`ActualReturnDate < ExpectedReturnDate.AddYears(-1)`) збережено без змін, щоб не змінювати поведінку. Число «1 рік» можна у майбутньому винести в іменовану константу.

### Чому це проблема на практиці

- **Ризик регресії.** Щоб додати страхування життя, треба відкрити робочий метод і додати гілку. Одна помилка може зламати розрахунок для всіх інших полісів, тому доведеться перетестовувати все.
- **Конфлікти в команді.** Кілька розробників, які додають різні типи полісів, правитимуть той самий метод.
- **Складність тестування.** Правило кожного типу полісу не можна перевірити окремо від решти.
- **Метод росте необмежено.** Кожен новий тип збільшує складність методу.

### 3.1. Нова структура

```java
if (type == PolicyType.AUTO) { ... }
```

## 4. Застосування принципів SOLID

### S: Single Responsibility
Кожен клас має одну причину для змін:
- правило страхування змінилося: змінюється лише відповідна `*PremiumStrategy`;
- змінилося округлення: змінюється лише `InsurancePremiumCalculator`;
- змінився формат або місце виводу логу: змінюється лише `PremiumLogger` і його реалізація.

### O: Open/Closed (основне завдання)
- **Точка розширення:** інтерфейс `PremiumStrategy`.
- **Додавання нового типу полісу** (на прикладі `LIFE`) потребує:
  1. нового класу `LifePremiumStrategy implements PremiumStrategy`;
  2. реєстрації стратегії в точці збірки (`Main`);
  3. нового значення в `enum PolicyType`: це одна константа без логіки.
- **Код `InsurancePremiumCalculator` і чотирьох існуючих стратегій не змінюється:** жодного рядка. Це підтверджено в `Main`: без реєстрації `LIFE` калькулятор видає помилку, після реєстрації розраховує премію.

### L: Liskov Substitution
Усі стратегії взаємозамінні: приймають коректного `PolicyHolder` і повертають невід'ємну премію без додаткових передумов. Немає `NotImplementedException`, немає стратегій із посиленими передумовами. Коректність вхідних даних гарантує сам `PolicyHolder` (див. нижче).

### I: Interface Segregation
`PremiumStrategy` має лише два методи, обидва обов'язкові для кожної реалізації. `PremiumLogger` має один метод. Порожніх методів-заглушок немає.

### D: Dependency Inversion
- `InsurancePremiumCalculator` залежить від абстракцій `PremiumStrategy` і `PremiumLogger`, а не від конкретних класів і `System.out`.
- Залежності передаються через конструктор (Constructor Injection).
- Конкретні об'єкти створюються тільки в `Main`.
- Service Locator не використовується.
- Для тестів можна підставити будь-який `PremiumLogger` (наприклад, лямбду `m -> {}`), що й зроблено в перевірці еквівалентності.

## 5. Прагматичні принципи

### DRY
- **Єдине місце округлення.** `setScale(2, HALF_UP)` було в одній гілці-фіналі; тепер воно в оркестраторі, і жодна стратегія його не дублює.
- **Єдине джерело правди для бізнес-правил.** Кожне правило (ставка, надбавка, вікові пороги) існує лише в одній стратегії як іменована константа. Число `1.20` або `25` більше не зустрічається як «голе» значення.
- **Єдине місце повідомлення про помилку** для незареєстрованого типу.

### KISS
- Усунено ланцюг `if/else if` і вкладені умови: метод оркестратора має лінійну логіку без розгалужень, окрім перевірки на `null`.
- Умови розрахунку записані короткими виразами: наприклад, у `HealthPremiumStrategy` гілку «якщо вік > 40» замінено на `Math.max(0, age - 40)`, що дає той самий результат без вкладеного `if`.
- Кожна стратегія мала малий розмір (кілька рядків) і зрозумілу структуру.
- Для реєстру використано стандартний `EnumMap`; жодних рефлексій, сканування класпасу або IoC-контейнерів.

### YAGNI
- Не додано абстрактних базових класів для стратегій, фабрик, конфігураційних файлів і IoC-контейнера: вони не потрібні для поточного завдання.
- Абстракції (`PremiumStrategy`, `PremiumLogger`) необхідні: перша є вимогою OCP, друга виносить побічний ефект (вивід) з бізнес-логіки.
- Немає заглушок «на майбутнє» і `NotImplementedException`.
- `LifePremiumStrategy` існує як навчальна демонстрація OCP за вимогою завдання; її правило (1% від суми + $5 за кожен рік після 50) умовне і не взяте з предметної області.

## 6. Відмінності від вихідної поведінки

Бізнес-результат розрахунку **не змінився**. Свідомо змінено таке:

1. `PolicyHolder` тепер відхиляє некоректні дані (від'ємний вік або сума, `null`, порожній ідентифікатор). Раніше такі об'єкти створювалися без помилок.
2. Геттер `isHasPriorClaims()` перейменовано на `hasPriorClaims()`.
3. Калькулятор тепер створюється з переліком стратегій і логером через конструктор, а не конструктором за замовчуванням. Конструктор і допоміжні типи (`PremiumStrategy`, `PremiumLogger`, стратегії, `PolicyType`) package-private: збирати об'єкти може лише код того ж пакета (`Main`).
4. Для додавання нового типу полісу в `enum PolicyType` додається одна константа. Це єдина зміна в існуючому коді, і вона не містить логіки розрахунку. Якщо потрібна повна відсутність змін навіть тут, ключем можна зробити рядок або інтерфейс замість `enum`, але це ускладнило б код без потреби (YAGNI).

# Завдання 3. Liskov Substitution Principle (LSP) — Варіант 6: Vehicle Fleet

## 1. Предметна область

Автоматизована система управління транспортним парком: заправка, керування (поїздки) та облік залишку палива чи заряду для паливних транспортних засобів та електромобілів.

## 2. Проблеми вихідного («поганого») коду

Клас `ElectricVehicle` успадковувався від `Vehicle`, який описує авто з паливним баком, хоча електромобіль баку не має.

| № | Проблема | Де проявляється | Порушений принцип |
|---|----------|-----------------|-------------------|
| 1 | `ElectricVehicle.Refuel` кидає `NotSupportedException`: нащадок не виконує контракт базового методу | `ElectricVehicle.Refuel` | **LSP** (головне порушення завдання) |
| 2 | Електромобіль передає в базовий конструктор «фіктивний» бак `base(licensePlate, 0, 0)` | конструктор `ElectricVehicle` | LSP, коректність моделі |
| 3 | Успадкований `Drive` не працює для електромобіля: він рахує витрату палива, а рівень палива дорівнює 0, тому будь-яка поїздка закінчується `InvalidOperationException("Not enough fuel to drive!")`. Нащадок, що не може виконати базову операцію, не можна підставити замість базового типу | успадкований `Drive` | **LSP** (порушена постумова) |
| 4 | Клієнт `GasStationManager` приймає будь-який `Vehicle` і розраховує на заправку рідким паливом. Для електромобіля `needed = 0 − 0 = 0`, тож заправка мовчки нічого не робить, і помилка замасковується | `RefuelVehicleToFull` | LSP, клієнтський код змушений знати про підтипи |
| 5 | Публічні сетери `TankCapacityLiters` і `LicensePlate` дозволяють зламати інваріант `Level ≤ Capacity` після створення | властивості `Vehicle` | інваріанти доменної моделі |
| 6 | Конструктор нічого не перевіряє: можна створити авто з `fuelLevel = 100` у баку на 50 л або з порожнім номером | конструктор `Vehicle` | fail-fast |
| 7 | `Drive` не перевіряє дистанцію: від'ємна відстань *збільшує* рівень палива | `Vehicle.Drive` | fail-fast, інваріанти |

### Чому це проблема на практиці

- **Збій у клієнтському коді.** Будь-який код, що працює з `Vehicle` (парк, станція, диспетчер), може отримати електромобіль і зламатися на `Refuel` або `Drive`.
- **Перевірки типу.** Щоб захиститися, клієнт змушений писати `if (vehicle is ElectricVehicle)`, а це знищує сенс поліморфізму.
- **Тихі помилки.** Заправка електромобіля «успішно» нічого не робить.
- **Невалідний стан.** Об'єкти з неможливими значеннями (рівень більший за ємність) потрапляють у систему й ламають розрахунки далі.

## 3. Що було зроблено

### 3.1. Аналіз порушення контракту

Контракт `Vehicle` обіцяв: *«кожен транспортний засіб можна заправити рідким паливом і він здатен їхати, споживаючи паливо з бака»*. Електромобіль цього виконати не може, тому підстановка `ElectricVehicle` замість `Vehicle` порушує поведінку програми. Причина в хибній ієрархії, а не в реалізації: «має паливний бак» не властиве кожному транспортному засобу.

### 3.2. Нова структура

| Тип | Роль |
|---|---|
| `Reservoir` (`sealed record`) | **Незмінний Value Object**: ємність + поточний рівень (літри чи кВт·год). Інваріант `0 ≤ Level ≤ Capacity` перевіряється в конструкторі (fail-fast). Методи `Add` і `Remove` повертають *новий* об'єкт |
| `Vehicle` (`abstract`) | Базовий тип, що містить лише те, що вміє **кожен** транспортний засіб: номерний знак і `Drive`. Номер перевіряється в конструкторі |
| `FuelVehicle : Vehicle` | Паливний ТЗ: має бак (`Reservoir`) і вміє `Refuel` |
| `ElectricVehicle : Vehicle` | Електромобіль: має батарею (`Reservoir`) і вміє `ChargeBattery`. Метод `Refuel` не успадковує |
| `GasStationManager` | Клієнт: приймає лише `FuelVehicle`, тобто тільки те, що справді можна заправити |
| `Program` | Демонстрація: загальна поїздка для всього парку через `Vehicle`, заправка лише паливних, зарядка лише електричних, fail-fast при некоректних даних |

### 3.3. Було і стало (ключовий фрагмент)

**Було:**

```csharp
public class ElectricVehicle : Vehicle
{
    public ElectricVehicle(string licensePlate, double batteryLevelKWh)
        : base(licensePlate, 0, 0) { ... }          // фіктивний бак

    public override void Refuel(double liters)
    {
        throw new NotSupportedException("...");     // порушення LSP
    }
}
```

**Стало:**

```csharp
public abstract class Vehicle
{
    public abstract void Drive(double distanceKm);   // лише спільний контракт
}

public class FuelVehicle : Vehicle      { public void Refuel(double liters) {...} }
public class ElectricVehicle : Vehicle  { public void ChargeBattery(double kWh) {...} }

public void RefuelVehicleToFull(FuelVehicle vehicle) { ... }  // тільки паливні
```

Некоректний стан тепер створити неможливо:

```csharp
public Reservoir(double capacity, double level)
{
    if (capacity <= 0) throw new ArgumentOutOfRangeException(nameof(capacity), ...);
    if (level < 0 || level > capacity) throw new ArgumentOutOfRangeException(nameof(level), ...);
    ...
}
```

### 3.4. Способи усунення порушення

Із варіантів, названих у завданні, застосовано одразу три:

1. **Розділення ієрархії.** `Refuel` більше не є членом базового типу; він є лише у `FuelVehicle`.
2. **Композиція замість успадкування.** Бак і батарея винесені в окремий об'єкт `Reservoir`, який входить до складу транспортного засобу.
3. **Незмінний Value Object із Guard Clauses.** `Reservoir` гарантує інваріант `0 ≤ Level ≤ Capacity` (fail-fast).

## 4. Застосування принципів SOLID

### L: Liskov Substitution (основне завдання)

- Усі нащадки `Vehicle` виконують його контракт: `Drive(distanceKm)` працює і для `FuelVehicle`, і для `ElectricVehicle`. У `Main` парк обходиться циклом по `Vehicle` без перевірок типу.
- Передумови не посилюються: обидва типи однаково вимагають додатну дистанцію (перевірка в базовому класі `EnsurePositiveDistance`).
- Постумови не слабшають: після `Drive` рівень ресурсу зменшується на розраховану витрату або викидається виняток.
- Немає `NotImplementedException` / `NotSupportedException`.
- Інваріанти зберігаються: стан ресурсу змінюється лише через `Reservoir`.

### S: Single Responsibility

`Reservoir` відповідає за інваріант рівня, `Vehicle` за ідентифікацію, `FuelVehicle` та `ElectricVehicle` за споживання свого типу ресурсу, `GasStationManager` за заправку.

### O: Open/Closed

Новий тип транспорту (наприклад, гібрид чи водневий) додається новим класом-нащадком `Vehicle` без змін в існуючих класах.

### I: Interface Segregation

Базовий тип має мінімальний контракт (лише `Drive`). Специфічні дії (`Refuel`, `ChargeBattery`) винесені у конкретні типи, тому клієнти не залежать від методів, які їм не потрібні.

### D: Dependency Inversion

Цей принцип у завданні не застосовувався: `GasStationManager` залежить від конкретного класу `FuelVehicle`. Для єдиної реалізації інтерфейс був би надлишковим (YAGNI). Інверсію залежностей виконано у Завданні 5.

## 5. Прагматичні принципи

### DRY

- **Єдине джерело правди для інваріанта** `0 ≤ Level ≤ Capacity` і правил `Add`/`Remove`: клас `Reservoir`. Паливний бак і батарея використовують ту саму логіку, замість того щоб дублювати її в кожному класі.
- **Єдине місце перевірки дистанції:** `Vehicle.EnsurePositiveDistance`.
- **Єдине місце перевірки номерного знака:** конструктор `Vehicle`.

### KISS

- Конструктори й методи `Reservoir` використовують Guard Clauses: некоректні дані відсікаються на початку, основна логіка не вкладена.
- Прибрано «хитрий» код із фіктивним баком і виняткам у нащадку. Модель тепер збігається з реальністю: електромобіль має батарею, а не бак.
- Клієнтському коду не потрібні перевірки `is ElectricVehicle`.

### YAGNI

- Не створено окремих інтерфейсів `IRefuelable` / `IChargeable`: для одного клієнта й одного класу-реалізації вони були б надлишковими.
- Функціонал «технічний огляд» і «пробіг» з опису предметної області не додавався, оскільки жоден код його не використовує.
- Немає заглушок «на майбутнє» й методів із `NotImplementedException`.
- Схожість структури `FuelVehicle` та `ElectricVehicle` свідомо не винесено в окремий узагальнений клас: це була б передчасна абстракція.

## 6. Відмінності від вихідної поведінки

Основна бізнес-поведінка (споживання 8 л/100 км, заправка в межах місткості, виключення при нестачі палива) збережена. Свідомо змінено таке:

1. `Vehicle` став абстрактним: створити «загальний» транспортний засіб більше не можна. Метод `Refuel` перенесено у `FuelVehicle`.
2. Електромобіль тепер **може їхати** (раніше `Drive` завжди завершувався помилкою) і заряджається методом `ChargeBattery`.
3. Конструктори перевіряють дані (fail-fast): рівень більший за ємність, неприпустима ємність чи порожній номер викликають виняток.
4. `Drive` відхиляє нульову або від'ємну дистанцію (раніше від'ємна збільшувала рівень палива).
5. Публічні сетери `LicensePlate` і `TankCapacityLiters` прибрано: об'єкти стали незмінними щодо цих полів.
6. Тексти винятків змінилися: `"Tank overflow!"` → `"Capacity exceeded!"`, додано `"Not enough energy!"`.
7. `GasStationManager.RefuelVehicleToFull` приймає `FuelVehicle`, а не `Vehicle`, тож спроба передати електромобіль не скомпілюється.
8. Додано `Main` із демонстрацією підстановки та fail-fast.

# Завдання 4
## 1. Предметна область

Програмно-апаратні платіжні термінали та касові системи. Термінал проводить транзакції (кредитна картка, NFC, банківський переказ, подарунковий сертифікат) і друкує паперові чеки. Різні термінали підтримують різні можливості: веб-каса приймає картки та банківські перекази, але не має NFC-зчитувача і принтера; POS-термінал приймає картки та NFC і друкує чеки, але не проводить перекази і не приймає сертифікати.

## 2. Проблеми вихідного («поганого») коду

Усі можливості були описані в одному «жирному» інтерфейсі `IPaymentTerminal` із п'ятьма методами. Кожен термінал мусив реалізувати всі п'ять, тому методи, яких він не підтримує, були заглушками з `UnsupportedOperationException`.

| № | Проблема | Де проявляється | Порушений принцип |
|---|----------|-----------------|-------------------|
| 1 | Один інтерфейс змішує п'ять різних ролей (картка, NFC, переказ, сертифікат, друк). Клієнт, якому потрібна лише оплата карткою, змушений залежати від усіх п'яти методів | `IPaymentTerminal` | **ISP** (головне порушення завдання) |
| 2 | Термінал реалізує методи, яких не підтримує, і кидає `UnsupportedOperationException`. Це 5 заглушок із 10 реалізацій: 3 у `OnlineWebCheckoutTerminal`, 2 у `PosCardReader` | обидва термінали | **LSP** |
| 3 | Помилка «операція не підтримується» виявляється лише під час виконання. Код `web.processNfcTap(...)` компілюється без помилок і падає вже в роботі | виклики через `IPaymentTerminal` | fail-fast, безпека типів |
| 4 | Інтерфейс змішує платіжні операції та друк чеків: це різні причини для змін | `IPaymentTerminal` | **SRP** |
| 5 | Додавання нового методу в інтерфейс (наприклад, оплата криптовалютою) змушує змінювати **всі** наявні термінали, навіть ті, що її не підтримують | `IPaymentTerminal` і всі реалізації | **OCP** |
| 6 | Заглушки з винятками повторюються в кожному терміналі для кожної непідтримуваної операції | обидва термінали | **DRY** |
| 7 | Демонстраційний `main` викликає лише підтримувані методи, тому проблему не видно: жоден виклик не спричиняє `UnsupportedOperationException` | `main` | прихований дефект |
| 8 | Усі типи вкладені в один клас `ECommercePaymentTerminal` разом із `main` | весь файл | організація коду |

### Чому це проблема на практиці

- **Помилки в роботі, а не під час компіляції.** Код, який отримав `IPaymentTerminal`, не знає, що можна викликати. Один неправильний виклик (наприклад, друк чека на веб-касі) зупиняє оплату.
- **Захисний код у клієнтів.** Щоб уникнути винятків, клієнти змушені перевіряти `instanceof` або ловити `UnsupportedOperationException`. Це перекладає знання про термінали на того, хто їх використовує.
- **Каскад змін.** Новий метод в інтерфейсі означає правки у всіх терміналах і повторне тестування кожного.
- **Складність тестування.** Для тесту клієнта, якому потрібна лише оплата карткою, доводиться створювати мок з п'ятьма методами.
- **Контракт прихований.** Що саме підтримує термінал, видно тільки з тіла методів-заглушок, а не з типу.

| `Clients.java` | Клієнти: `CardCheckoutService` залежить лише від `CardPayment`, `ReceiptService` лише від `ReceiptPrinter` |
| `Main.java` | **Composition Root**: єдине місце, де створюються конкретні термінали й збираються залежності |

Групування типів у файлах таке: публічні класи `PaymentInterfaces`, `Terminals` і `Clients` є непідписуваними контейнерами (`final`, приватний конструктор), усередині яких оголошено вкладені типи. Так кілька типів лежать в одному файлі. Принципи SOLID від цього не залежать: інтерфейси й класи залишаються окремими типами. За потреби кожен тип можна винести в окремий файл без змін логіки.

### 3.2. Було і стало (ключовий фрагмент)

**Було:**

```java
public interface IPaymentTerminal {
    void processCreditCard(BigDecimal amount, String cardNumber);
    void processNfcTap(BigDecimal amount);
    void processBankTransfer(BigDecimal amount, String iban);
    void processGiftCard(BigDecimal amount, String voucherCode);
    void printPaperReceipt(String text);
}

public static class OnlineWebCheckoutTerminal implements IPaymentTerminal {
    // ...
    @Override public void processNfcTap(BigDecimal amount) {
        throw new UnsupportedOperationException("Web browser checkout cannot scan physical NFC cards.");
    }
    // ще дві заглушки: processGiftCard, printPaperReceipt
}
```

**Стало:**

```java
public interface CardPayment      { void processCreditCard(BigDecimal amount, String cardNumber); }
public interface NfcPayment       { void processNfcTap(BigDecimal amount); }
public interface BankTransferPayment { void processBankTransfer(BigDecimal amount, String iban); }
public interface GiftCardPayment  { void processGiftCard(BigDecimal amount, String voucherCode); }
public interface ReceiptPrinter   { void printPaperReceipt(String text); }

public static class OnlineWebCheckoutTerminal implements CardPayment, BankTransferPayment { ... }
public static class PosCardReader implements CardPayment, NfcPayment, ReceiptPrinter { ... }
```

Тепер непідтримувана операція просто відсутня в типі терміналу, і спроба її викликати не скомпілюється. У `Main` це показано закоментованим рядком `new ReceiptService(web)`: веб-каса не реалізує `ReceiptPrinter`, тому компілятор відхилить такий код.

## 4. Застосування принципів SOLID

### S: Single Responsibility
- Кожен інтерфейс описує одну роль: оплата карткою, NFC, переказ, сертифікат або друк чека. Платіжні операції та друк більше не змішані в одному контракті.
- Кожен клієнт відповідає за один сценарій: `CardCheckoutService` проводить оплату карткою, `ReceiptService` друкує чек.
- Змінилися правила друку чеків: це стосується лише `ReceiptPrinter`, `ReceiptService` і терміналів із цією роллю.

### O: Open/Closed
- **Точка розширення:** набір role-інтерфейсів у `PaymentInterfaces`.
- **Новий спосіб оплати** (наприклад, `CryptoPayment`) додається новим інтерфейсом. Наявні інтерфейси, клієнти й термінали, які його не підтримують, не змінюються.
- **Новий термінал** додається новим класом, який реалізує потрібні ролі. Існуючі термінали й клієнти не змінюються.
- Обмеження, яке варто чесно зазначити: якщо наявний термінал має почати підтримувати нову роль, його клас доведеться доповнити `implements`. Це природна зміна, бо змінюється саме можливість цього терміналу.

### L: Liskov Substitution
- Заглушок із `UnsupportedOperationException` більше немає. Кожен термінал виконує всі методи інтерфейсів, які реалізує.
- Будь-яка реалізація `CardPayment` взаємозамінна для `CardCheckoutService`. У `Main` це показано: той самий `CardCheckoutService` працює і з `web`, і з `pos`.
- Те саме для `ReceiptPrinter`: підставити можна будь-який термінал, що друкує чеки.
- Застереження: перевірки вхідних даних (`amount`, `cardNumber`) у проєкті немає ні в початковій, ні в новій версії, тому контракт щодо коректності аргументів лише неявний. Тести в цій роботі не додавалися.

### I: Interface Segregation (основне завдання)
- «Жирний» `IPaymentTerminal` замінено п'ятьма вузькими інтерфейсами по одному методу.
- Клієнт залежить лише від того, що викликає: `CardCheckoutService` бачить тільки `processCreditCard`, `ReceiptService` тільки `printPaperReceipt`.
- Термінал реалізує лише ті ролі, які підтримує: `OnlineWebCheckoutTerminal` не знає про NFC і друк, `PosCardReader` не знає про перекази й сертифікати.
- Помилка використання виявляється під час компіляції, а не під час виконання.

### D: Dependency Inversion
- `CardCheckoutService` залежить від абстракції `CardPayment`, `ReceiptService` від `ReceiptPrinter`, а не від `OnlineWebCheckoutTerminal` чи `PosCardReader`.
- Залежності передаються через конструктор (Constructor Injection) з перевіркою `Objects.requireNonNull`.
- Конкретні термінали створюються тільки в `Main`.
- Service Locator не використовується.
- Для тестів клієнтів можна підставити лямбду або мінімальну реалізацію одного вузького інтерфейсу.
- Застереження: самі термінали, як і раніше, пишуть у `System.out` напряму. Це імітація виконання операції, тому вивід не виносився в окрему абстракцію.

## 5. Прагматичні принципи

### DRY
- Дублювані заглушки з `UnsupportedOperationException` (5 штук з повторюваними текстами) прибрано повністю: непідтримувані операції більше не потрібно «оголошувати».
- Знання про те, що підтримує термінал, тепер зберігається в одному місці: у списку `implements` його класу.

### KISS
- Без `instanceof`, перевірок `try/catch` для `UnsupportedOperationException` і прапорців можливостей: тип сам каже, що термінал уміє.
- Кожен інтерфейс має один метод, кожен клієнт має один метод. Класи короткі й читаються за кілька секунд.
- Жодних рефлексій, адаптерів чи IoC-контейнерів.

### YAGNI
- Не створено абстрактного базового класу терміналу, фабрик терміналів, спільного інтерфейсу-«об'єднання» і IoC-контейнера: для поточного завдання вони не потрібні.
- Клієнти створено лише для двох ролей (`CardPayment`, `ReceiptPrinter`), які демонструють ISP. Для NFC, переказу й сертифіката клієнтів немає, бо в початковому коді їх теж не було.
- Інтерфейс `GiftCardPayment` збережено, бо така можливість була в початковому контракті, але жоден термінал його зараз не реалізує. Це свідомо: майбутній термінал із сертифікатами зможе його реалізувати без змін в існуючому коді.
- Якщо клієнту потрібно кілька ролей одразу (наприклад, оплата карткою й друк чека), це можна виразити параметром із перетином типів `<T extends CardPayment & ReceiptPrinter>`. У цій роботі такого клієнта немає, тому він не додавався.

## 6. Відмінності від вихідної поведінки

Бізнес-поведінка терміналів **не змінилася**: тексти повідомлень, які друкують термінали, ті самі. Свідомо змінено таке:

1. Інтерфейс `IPaymentTerminal` видалено. Код, який тримав термінал за цим типом, тепер має використовувати потрібну роль: `CardPayment`, `NfcPayment`, `BankTransferPayment`, `GiftCardPayment` або `ReceiptPrinter`.
2. Виклики непідтримуваних операцій (наприклад, `processNfcTap` на веб-касі, `printPaperReceipt` на веб-касі, `processBankTransfer` на POS) тепер **не компілюються**, а раніше падали з `UnsupportedOperationException` під час виконання.
3. Термінали винесено з класу `ECommercePaymentTerminal` у `Terminals` і додано пакет `variant6_ecommercepaymentterminal`. Клієнтський код має змінити імпорти.
4. Додано клієнтів `CardCheckoutService` і `ReceiptService`, які приймають залежність через конструктор і відхиляють `null`. Раніше аналогів не було.
5. Демонстраційний `main` перенесено в `Main` і змінено: він показує збирання залежностей і перевірку компілятором замість прямих викликів методів терміналів.

# Завдання 5. Dependency Inversion Principle (DIP) — Варіант 6: Document Approval Workflow

## 1. Предметна область

Корпоративна система електронного документообігу: керівник узгоджує документ. Система перевіряє права підписанта (Active Directory), оновлює пошуковий індекс (Elasticsearch) і надсилає сповіщення в робочий чат (Slack).

## 2. Проблеми вихідного («поганого») коду

Клас `DocumentApprovalWorkflow` сам створював усі свої залежності через `new` у конструкторі.

| № | Проблема | Де проявляється | Порушений принцип |
|---|----------|-----------------|-------------------|
| 1 | Високорівневий клас бізнес-логіки напряму залежить від низькорівневих реалізацій (`ElasticsearchDocumentIndex`, `ActiveDirectoryUserValidator`, `SlackWebhookNotifier`) | поля й конструктор `DocumentApprovalWorkflow` | **DIP** (головне порушення завдання) |
| 2 | Конструктор сам виконує `new` для трьох об'єктів: жорстке зв'язування (Tight Coupling) | `DocumentApprovalWorkflow()` | DIP |
| 3 | Підмінити реалізацію (наприклад, Slack → Teams, Elasticsearch → БД) неможливо без правки класу бізнес-логіки | весь клас | DIP, OCP |
| 4 | Модульне тестування неможливе без реальних AD, Elasticsearch і Slack | весь клас | тестованість |
| 5 | Перевірка `string.IsNullOrEmpty` пропускає ідентифікатор із самих пробілів | `ApproveDocument` | fail-fast, коректність |

### Чому це проблема на практиці

- **Неможливість тестувати.** Щоб перевірити логіку затвердження, потрібні робочі AD, пошуковий кластер і Slack.
- **Складна зміна технологій.** Заміна одного сервісу змушує редагувати й повторно тестувати клас бізнес-логіки.
- **Зворотний напрямок залежностей.** Бізнес-правила, які мають бути стабільними, залежать від технічних деталей, що змінюються частіше.
- **Приховані залежності.** За конструктором без параметрів не видно, що клас потребує три зовнішні системи.

## 3. Що було зроблено

### 3.1. Нова структура

| Тип | Роль |
|---|---|
| `IDocumentIndex` | Абстракція пошукового індексу (`IndexDocument`) |
| `IUserValidator` | Абстракція перевірки прав підписанта (`ValidateUserSignature`) |
| `INotificationService` | Абстракція надсилання повідомлень (`PostChannelMessage`) |

| `DocumentApprovalWorkflow` | Високорівнева бізнес-логіка: залежить лише від інтерфейсів, залежності отримує через конструктор |
| `Program.Main` | **Composition Root**: єдине місце, де створюються конкретні об'єкти й збираються залежності |

### 3.2. Було і стало (ключовий фрагмент)

**Було:**

```csharp
private readonly ElasticsearchDocumentIndex _searchIndex;
private readonly ActiveDirectoryUserValidator _adValidator;

public DocumentApprovalWorkflow()
{
    _searchIndex = new ElasticsearchDocumentIndex();
```

```csharp
private readonly IDocumentIndex _searchIndex;

private readonly INotificationService _slackNotifier;

public DocumentApprovalWorkflow(
    IDocumentIndex searchIndex,
    IUserValidator adValidator,
    INotificationService slackNotifier)

    _searchIndex = searchIndex ?? throw new ArgumentNullException(nameof(searchIndex));
    _adValidator = adValidator ?? throw new ArgumentNullException(nameof(adValidator));
```

```csharp
// Production
var productionWorkflow = new DocumentApprovalWorkflow(

    new ActiveDirectoryUserValidator(),
    new SlackWebhookNotifier());

// Test: той самий клас бізнес-логіки, інші залежності
var testWorkflow = new DocumentApprovalWorkflow(
```

## 4. Застосування принципів SOLID

### D: Dependency Inversion (основне завдання)

- `DocumentApprovalWorkflow` залежить від абстракцій `IDocumentIndex`, `IUserValidator` і `INotificationService`, а не від конкретних класів.
- Низькорівневі класи також залежать від абстракцій: вони реалізують ці інтерфейси. Напрямок залежностей інвертовано.
- Залежності передаються через конструктор (**Constructor Injection**) і перевіряються на `null` (fail-fast).
- Конкретні об'єкти створюються лише в `Main` (Composition Root). Service Locator не використовується.
- Реалізації підміняються без жодної зміни в `DocumentApprovalWorkflow`, що демонструють режими Production і Test.

### S: Single Responsibility

Клас бізнес-логіки лише координує узгодження. Індексація, перевірка прав і сповіщення ізольовані у своїх сервісах.

### O: Open/Closed

Новий канал сповіщень (наприклад, Teams) додається новою реалізацією `INotificationService` без змін в існуючому коді.

### L: Liskov Substitution

Production- та Mock-реалізації взаємозамінні: клас бізнес-логіки працює з будь-якою з них однаково.

### I: Interface Segregation

Кожен інтерфейс має один метод і відповідає одній ролі, тому порожніх методів-заглушок немає.

## 5. Прагматичні принципи

### DRY

- Кожна залежність має єдину абстракцію-контракт. Бізнес-логіка знає про сервіс лише через один інтерфейс.
- Перевірка вхідних залежностей зосереджена в одному місці: конструкторі класу.

### KISS

- Метод `ApproveDocument` має лінійний вигляд: перевірка документа → перевірка підписанта → індексація → сповіщення. Guard Clauses виключають вкладеність.
- Збірка виконується вручну (Manual DI) без IoC-контейнера: для трьох залежностей цього достатньо.

### YAGNI

- Інтерфейси необхідні: вони вимога DIP і дають змогу підставляти Mock-об'єкти. Кожен має реальну реалізацію в двох варіантах (Production і Test).
- Не додано фабрик, IoC-контейнера, конфігураційних файлів та Service Locator.
- Немає заглушок «на майбутнє» й методів із `NotImplementedException`.

## 6. Відмінності від вихідної поведінки

Послідовність кроків і тексти виводу не змінилися. Свідомо змінено таке:

1. Конструктор приймає залежності й кидає `ArgumentNullException`, якщо якусь не передано. Конструктора без параметрів більше немає.
2. Перевірку `string.IsNullOrEmpty(doc.DocumentId)` замінено на `string.IsNullOrWhiteSpace`: тепер ідентифікатор із самих пробілів вважається некоректним.
3. Додано Mock-реалізації та `Main`, яка демонструє підміну (Production-режим і Test-режим).
4. Імена полів `_adValidator` і `_slackNotifier` залишені з вихідного коду, хоча тип поля вже абстрактний. За бажанням їх можна перейменувати (наприклад, `_userValidator`, `_notifier`), щоб імена не вказували на конкретні технології.
5. Метод інтерфейсу `PostChannelMessage` із параметром `channel` відображає термінологію Slack. Це простий компроміс: інтерфейс залишено сумісним із вихідним кодом, щоб не змінювати його сигнатури.
