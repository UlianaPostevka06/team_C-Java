# ADR-001: Аудит legacy-коду бронювання столика та архітектурні рішення(C#)

## Статус
Прийнято (Accepted)

## Контекст
Вихідний код (`Variant6_RestaurantBooking`) складається з анемічних класів `Guest`, `MenuItem`, `OrderLine`, `TableReservation` та монолітного методу `LegacyRestaurantProcessor.ProcessReservationConsole()`. Початковий стан зафіксовано в Git окремим комітом перед рефакторингом.

Метрики до рефакторингу: CBO(`LegacyRestaurantProcessor`) = 4 (`Guest`, `TableReservation`, `MenuItem`, `OrderLine`); LCOM4 = 1 (єдиний метод). Показники формально в нормі лише тому, що весь код зібраний в одному методі з багатьма обов'язками.

## Виявлені проблеми

| Де | Проблема | Що застосуємо |
|---|---|---|
| `ProcessReservationConsole()` | Розрахунок суми, знижки, сервісного збору та `TotalBill` виконується зовні сутностей | Information Expert |
| `ProcessReservationConsole()` | Усі об'єкти створюються безпосередньо в одному методі, порожніми, з покроковим заповненням | Creator |
| `ProcessReservationConsole()` | Введення з консолі, бізнес-логіка та виведення змішані (Bloated Controller) | Controller, Pure Fabrication |
| `ProcessReservationConsole()` | Знижка та збір залежать від `if (TimeSlot == "HappyHours")` та `if (GuestsCount >= 5)`, магічні числа `0.85m`, `0.10m` | Polymorphism, Protected Variations |
| `ProcessReservationConsole()` | Збереження в `reservations.json` та SMS жорстко вбудовані в метод | Indirection, Protected Variations |
| `Guest`, `MenuItem`, `OrderLine`, `TableReservation` | Публічні `get; set;` дозволяють змінити стан ззовні, немає валідації (кількість ≤ 0, від'ємна ціна) | Інкапсуляція, Information Expert |
| `TableReservation` | `PreOrderedItems` це відкритий `List<OrderLine>`, його можна змінювати напряму; `TotalBill` можна розсинхронізувати з іншими сумами | Захист колекції, контрольоване додавання позицій |
| `TableReservation` | `TimeSlot`, `Status`, `CourseType` це магічні рядки без перевірки | `enum` + розбір у `ConsoleCommandParser` |
| `ProcessReservationConsole()` | Захардкоджені дані (`Id = 3`, телефон, 6 гостей, страви); депозит із опису завдання відсутній | Controller + DTO команди, політика депозиту |

## Рішення

### Рішення 1. Хто рахує суму бронювання (Information Expert)
* **Question:** Хто відповідає за підсумок замовлення, знижку та `TotalBill`?
* **Alternatives:**
  * A: залишити в `LegacyRestaurantProcessor`;
  * B: покласти на `Guest`;
  * C: `OrderLine.Subtotal()` + `TableReservation` рахує підсумки.
* **Вибір:** **C**, бо `OrderLine` знає ціну й кількість, а `TableReservation` володіє всіма рядками, гостями й часовим слотом. `Guest` цих даних не має.
* **Переваги:** формула біля даних, `TotalBill` завжди узгоджений, правила тестуються без консолі.
* **Компроміси:** `TableReservation` отримує залежність від `OrderLine` та інтерфейсів політик, CBO зростає (контролюємо ≤ 4).

### Рішення 2. Створення об'єктів і захист стану (Creator)
* **Question:** Як гарантувати, що бронювання завжди валідне?
* **Alternatives:**
  * A: залишити публічні сеттери, валідувати в сервісі;
  * B: конструктор із усіма параметрами;
  * C: статичні фабрики `TableReservation.Create(...)`, `AddItem(...)`, `private set`, `IReadOnlyList<OrderLine>`.
* **Вибір:** **C**, бо агрегат сам створює й містить `OrderLine`, а перевірки (`count > 0`, `guestsCount ≥ 1`) виконуються в одному місці.
* **Переваги:** невалідний об'єкт неможливо створити; колекцію не змінити в обхід правил.
* **Компроміси:** більше коду, ніж у простих DTO; всі місця створення об'єктів треба переписати.

### Рішення 3. Розділення UI, сценарію та інфраструктури (Controller, Indirection, Pure Fabrication)
* **Question:** Як розділити консоль, координацію сценарію, збереження та сповіщення?
* **Alternatives:**
  * A: розбити метод на приватні методи в одному класі;
  * B: віддати збереження й SMS самій сутності `TableReservation`;
  * C: тонкий `ConsoleUi` + `ConsoleCommandParser` → `ReservationController` → інтерфейси `IReservationRepository`, `INotificationSender`, `IReceiptFormatter`.
* **Вибір:** **C**, бо контролер координує сценарій без введення/виведення, а інфраструктура ховається за інтерфейсами.
* **Переваги:** сховище, канал сповіщення й формат чека змінюються без зміни ядра; кожен клас має одну причину для зміни (LCOM4 = 1).
* **Компроміси:** більше класів та інтерфейсів; для невеликої задачі це надлишково, але вимагається завданням і полегшує тестування.

### Рішення 4. Правила знижки, збору та депозиту (Polymorphism, Protected Variations)
* **Question:** Як додавати нові правила без зміни ядра?
* **Alternatives:**
  * A: залишити `if/switch`;
  * B: `enum` + словник коефіцієнтів;
  * C: інтерфейси `IDiscountPolicy`, `IServiceChargePolicy`, `IDepositPolicy` з реалізаціями (`HappyHoursDiscount`, `LargeGroupServiceCharge`, ...) та фабрика вибору за `TimeSlot`.
* **Вибір:** **C**, бо потрібні й різні формули, а не лише різні коефіцієнти (наприклад, поріг за кількістю гостей).
* **Переваги:** новий слот (`Brunch`) додається новим класом без зміни `TableReservation`; пороги й відсотки передаються конструктором, без магічних чисел.
* **Компроміси:** кілька додаткових класів; розмір депозиту (наприклад, 20% для груп ≥ 5 гостей) є припущенням команди, його варто узгодити з викладачем.

## Наслідки
* **Позитивні:** знижено зачеплення бізнес-логіки з консоллю й інфраструктурою; інваріанти захищені сутностями; правила ціноутворення ізольовані за стабільними контрактами; ціль CBO ≤ 4 та LCOM4 = 1 для доменних класів.
* **Негативні / компроміси:** зростає кількість класів; потрібно підтримувати дисципліну залежностей між шарами (CLI → Application → Domain).
